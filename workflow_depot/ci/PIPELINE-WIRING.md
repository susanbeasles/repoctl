# Source wiring and commissioning boundary

The integration caller runs only on an exact signed candidate push under `int/**`: source admission, required project quality commands and one build in the approved image, immutable build inventory, full original security policy with build-byte verification/scanning, optional approved reviewer, then private SBOM/checksum/release material signing. All 76 original module files are preserved. Source-only layout checks do not qualify live producers.

Dynamic scanners accept only an explicitly approved HTTPS private IPv4 target, with no DNS/public/credential fallback. Both direct security callers and the integration wrapper enforce the guard. This source does not create a preview endpoint, invent an origin, authorize a scan or claim that a supplied approval reference establishes isolation. Commission a real isolated synthetic preview and verify its access boundary separately.

The owned CodeQL Advanced configuration retains default queries plus security-extended, with no path/query exclusions. A deterministic runtime adapter adds only `config-file` to the original composite; its pinned action, mandatory result statuses and compiled-build/eligibility failures are unchanged. Private-repository entitlement and additional query-pack/version policy require explicit review; no scanner replacement or licensing workaround is implied. GitHub's [Advanced setup documentation](https://docs.github.com/en/code-security/code-scanning/creating-an-advanced-setup-for-code-scanning/customizing-your-advanced-setup-for-code-scanning) describes configuration files.

The pinned reviewer is disabled by default. Opt-in requires an immutable container, a source-disclosure approval and reviewed argv from that qualified runtime. It receives only the existing optional review key and basic runtime environment, emits a SHA-bound advisory report, and has no OIDC/deployment permission. No reviewer image, command, provider subscription or secret is invented. Missing/malformed review blocks release material packaging when opted in; advisory text does not authorize promotion.

`acceptedMainArtifacts` constructs the existing canonical deployment verifier with installed policy/GitHub/signing-receipt/provenance readers. It verifies current main, enrolled signer, retained hardware/owner approval, paired tags, successful exact integration jobs and pinned workflow provenance before retrieving bytes; it rechecks after retrieval. Its promotion envelope uses the unchanged canonical packager. Packaging confers no authority and central verification remains independent. `ci/source-components.json` records the exact canonical source revision and hashes; it does not rewrite historical repoctl-source.json provenance.

`main-deployment.yml` composes accepted-main artifact consumption and central dispatch. Required inputs identify the actual successful integration run, immutable producer/consumer revisions, existing retained promotion-evidence artifact, real Worker-artifact path and registered target. There are no invented defaults. `accepted-main-artifacts.yml` verifies same-repository/same-SHA integration success and current main, checks exact OIDC producer signatures, extracts/checksums within bounds, packages retained receipt/owner/provenance files into the existing deployment-bundle schema, rechecks main, then uploads `deployment-<sha>-<target>`. It executes no build. The evidence producer must supply signing-receipt.json, approval-payload.json, owner-approval.json and provenance.json from the retained approved operation; absent files fail. The central controller independently validates their authority and exact bytes.

`request-deployment.yml` is the exact-main thin caller. Only the existing dispatch capability reaches the fixed delivery_control/deploy.yml endpoint; provider credentials remain central. The new main composition dispatches only after artifact packaging succeeds. It does not enable registered targets. The existing signer caller migration is separately reviewed and central signer Container support remains blocked; the retained Worker-artifact schema is not falsely extended to Containers.

The deployment Environment loader uses only the official 1Password CLI, not SDK or Connect. Its Linux amd64 CLI 2.41.0 Debian package URL/digest were checked against the vendor package index and the existing verified local package. Public tool download/extraction receives no credentials; only the qualified CLI receives the bootstrap token. Allowed provider values travel through a captured private pipe, with no secret file or argv. Bootstrap/Connect variables are removed from the deployment child. Missing configuration, invalid account/data/tool digest or CLI failure blocks without fallback. Tests use synthetic values and do not load an actual Environment.

Live gates remain separate: approved private preview, actual reviewer runtime/disclosure authorization, CodeQL entitlement/query-pack policy, independent signed receipt/evidence producers, enrolled App/owner authority, private source-publisher/archive bindings and central target/OIDC/journal commissioning. No application caller activation beyond the separately requested signer source migration, live scan, deployment, hook change, credential provisioning, ruleset change, main push or merge was performed.
